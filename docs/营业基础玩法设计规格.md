# 星灯火锅店 · 营业基础玩法设计规格（v0.4 对齐稿）

> 本文档是「给 Codex 的实现依据 + 给 Kimi/Claude 的复核清单」。
> 范围：只做**营业期**的血肉玩法，不碰剧情（B 阶段）、不碰美术、不碰农场/牧场/工坊（D 阶段）。
> 现状基线：`main` = 66a77f9 之后，A1/A2/A3/A4/A5/A7 已勾选。

---

## 0. 现状诊断（为什么这样拆）

现在「营业一晚」的骨架是通的，但营业期玩家几乎**没有可操作内容**：

| 环节 | 现状 | 空洞 |
|---|---|---|
| 主菜 | 只有 3 种（牛肉 / 虾 / 清炖霜牛） | 菜单选择薄，`mains=[1,2,6]` 硬编码 |
| 特别菜单 | 固定 3 种，`BASE=[1,5,2]`、`CORES` 硬编码 | 研发产出有限，无扩展 |
| 烹饪 | 只有清炖霜牛 1 种有火候小游戏，其余「一键装盘」 | 营业期玩家无事可做 |
| 员工 | 只有露米 1 个补餐员；点单/送餐是自动 worker | 岗位/雇佣/成长无决策 |
| 顾客口味 | `ticket%N` 伪随机，偏好→点单→加料因果很浅 | 「读懂口味」没立起来 |

四个模块是一条**闭环依赖链**，不是四条平行线。

---

## 1. 依赖顺序（实现顺序必须按此）

```
M1 扩菜谱 + 特别菜单      ← 数据层，所有后续模块的地基
   ↓
M2 顾客口味决策           ← 规则层，把口味映射到 M1 的菜谱
   ↓
M3 烹饪 / 备菜玩法        ← 交互层，把 M1 的菜谱变成有操作的手感
   ↓
M4 员工岗位与雇佣         ← 管理层，整合 M1–M3 的产出流
```

- M1、M2 必须一起上（口味需要菜谱才有意义）。
- M3 依赖 M1（要有足够多的菜谱，烹饪才有内容）。
- M4 建议最后，因为它要整合前三个的产出/消耗节奏。

每个模块单独成 PR，各自带测试 + CI 绿，再合下一个。

---

## 2. 通用约定（所有模块必须遵守）

1. **存档 schema 升级到 `version=5`**，并保持对 v1–v4 旧档的**迁移兼容**（`apply_save` 给新字段默认值，`save_store.validate` 放行旧结构）。
2. **不破坏现有 13 个测试 suite**；新规则一律新增 `tests/` 用例，不删旧断言除非规则本身被替换（需在 PR 说明里写清）。
3. **数字守恒**：所有改动不得出现原料/成品/金币凭空增减。每个改动对应一条「输入 X → 输出 Y，且 X==Y」的断言。
4. **不写新场景节点**：玩法逻辑尽量放进 `systems/` 下新脚本（`recipes.gd` 扩展或新文件），`main.gd` 只做接线；等 M4 收尾时再统一拆 `main.gd`。
5. **口味/菜谱数据用表驱动**，不写进 `tick_business` 的 if 链。
6. 每个 PR 顶部写清「规则变化 + 存档字段变化 + 测试新增」三行摘要。

## 3. M1 · 扩菜谱 + 特别菜单

### 玩法目标
让「今晚菜单」有真实取舍：菜品种类变多，但**备菜产能有限**，玩家要在「多而全」和「少而精」之间选择。

### 规则设计
- **主菜**从 3 种扩到 **6 种**（对应 6 种基础食材的组合产出，先做 6 种「直接主菜」：灯笼菇、霜牛、跳跳虾、火椒、豆腐、萝卜各一道），`mains` 不再硬编码，改为「菜品定义表」。
- **菜品定义表**（新增 `systems/dishes.gd`）每道菜一个条目：
  - `id`、`name`、`kind`（主菜/自取/特别）、`core`（主料数组）、`cost`、`fill`、`tags`（口味标签）、`tier`（普通/招牌）。
- **特别菜单**：现有 `Recipes` 3 种保留，但 `CORES/FLAVORS/FORBIDDEN` 改为**表驱动**，并允许研发解锁**最多 6 种特别菜单**（先扩到 6，编号稳定，旧 3 种不动）。
- **菜单容量**：今晚普通主菜 + 自取菜 + 特别菜单各有**上限**（普通 6 选 4、自取 4 选 3、特别 6 选 3），逼玩家取舍。

### 数据接入
- 新增 `systems/dishes.gd`（菜谱定义 + 查询 API：`by_id` / `is_main` / `is_side` / `is_special`）。
- `main.gd` 里 `mains=[1,2,6]`、`SIDE_FOODS=[0,3,4,5]`、`BASE=[1,5,2]`、`SPECIALS=Recipes.NAMES` 全部改为从 `dishes.gd` 查。
- `regular_menu` 从 `[bool×7]` 扩展为能表达「主菜/自取/特别」三组选择的结构（建议 `menu: {mains:[], sides:[], specials:[]}`，旧字段保留做迁移）。

### 存档字段
- `version` → 5。
- 新增 `dishes_unlocked`（已研发菜谱 id 数组）、`menu`（今晚选择结构）。
- 迁移：旧 `regular_menu[7]` / `offerings[3]` / `formulas[3]` 映射到新 `menu` + `dishes_unlocked`。

### 验收测试（新增 `tests/dishes.gd`）
- [ ] 6 种主菜、4 种自取、6 种特别都能查到且 `kind` 正确。
- [ ] 菜单容量上限：普通 6 选 4、自取 4 选 3、特别 6 选 3 超选被拒。
- [ ] 旧档 v4（`regular_menu`/`offerings`/`formulas`）读入后正确迁移到新 `menu`。
- [ ] 存档往返后 `menu` / `dishes_unlocked` 一致。

## 4. M2 · 顾客口味决策

### 玩法目标
把「口味」从 `ticket%N` 的伪随机，变成**可读、可决策、可满足**的信号。

### 规则设计
- 每位顾客生成时带有**显式偏好档案**：`{ preference: 口味标签, dislikes: [口味标签], regular: 常点菜id|null, special_want: 特别菜id|null }`。
- 偏好**不再用 `ticket%4/%6` 决定**，改为可配置的「顾客模板表」（`systems/patrons.gd`），模板决定偏好分布，但**不要求每个客人唯一**。
- 点单规则：
  1. 若 `special_want` 有值且菜单有、库存够 → 优先点该特别菜。
  2. 否则在「普通主菜」里选 `preference` 命中的，其次随机。
  3. `dislikes` 命中的菜永不主动点（除非只剩它）。
- **反馈可见**：客人点单/用餐后在气泡或评价里能看出「喜欢/讨厌」的原因（复用现有 `liked` / `missed_taste` 语义，但改为由偏好驱动，不是纯随机）。

### 数据接入
- 新增 `systems/patrons.gd`（顾客模板 + 偏好生成）。
- `spawn_guest()` / `seat_next()` 里 `wish=1 if ticket%4==2 else ticket%6` 等，改为从偏好档案生成 `wish` 和 `craving`。
- `tick_table_service` 的主菜选择 `[g.wish, mains[first], ...]` 改为按偏好 + 菜单 + 库存排序取第一。
- `checkout` 里 `liked`/`missed_taste` 的判断改为对照偏好档案。

### 存档字段
- 顾客是营业期临时状态，**不进存档**（保持「营业过程不保存」的既有约定）。
- 顾客模板表是静态数据，不存档。

### 验收测试（新增 `tests/patrons.gd`）
- [ ] 偏好「辣味」的客人，在菜单含辣味主菜时点辣味菜。
- [ ] 讨厌「辣味」的客人，不会主动点辣味（除非库存只剩辣味）。
- [ ] `special_want` 有库存时优先点特别菜。
- [ ] 满足偏好 → `liked=true`；未满足 → `missed_taste` 增加。

## 5. M3 · 烹饪 / 备菜玩法

### 玩法目标
补上营业期最大空洞：让玩家在营业中有「忙碌起来」的操作。

### 规则设计（沿路线图「熟菜快做，研发和人物菜细做」）
- **普通主菜 = 快做**：营业期在后厨把「一键装盘」换成**短节奏操作**——选菜 → 一个 1.5–2 秒的火候条（成功/过火/夹生三档），成功正常出 2 盘，失误出 1 盘或废料。
- **特别菜 / 定制单 = 细做**：保留现有「原方 + 加料」的多步骤 + 火候条，加料影响口味标签（沿用 `recipes.gd`）。
- **火候小游戏统一**：把现有清炖霜牛的 `finish_cook` 逻辑抽成通用 `cook_dish(dish_id)`，所有菜共用一套「火候窗口 [40,70]」，不同菜可调窗口宽度（简单菜更宽、招牌菜更窄）。
- **快捷制作**：熟练度 `mastery` 按菜谱分别累计（从单一 `mastery` 改为 `mastery_by_dish`），某菜熟练 ≥3 解锁该菜「快速装盘」（跳过火候条）。

### 数据接入
- `finish_cook(success)` 泛化为 `finish_cook(dish_id, quality)`；`mastery` → `mastery_by_dish: Dictionary[int->int]`。
- 新增 `cook_dish(dish_id)` 状态机（沿用 `cooking/cook_time/cook_cursor`）。
- `show_kitchen()` / `show_preparation()` 的 UI 入口改为列全部可做菜谱，而非只炖菜。

### 存档字段
- `mastery` → `mastery_by_dish`（迁移：旧 `mastery` 映射为炖菜那道菜的熟练度）。

### 验收测试（新增 `tests/cooking.gd`）
- [ ] 普通主菜快做：火候落在窗口内 → 出 2 盘；过火/夹生 → 出 1 盘或废料。
- [ ] 特别菜加料后 `tags` 正确包含所加口味。
- [ ] 某菜熟练 ≥3 解锁快速装盘，且不消耗额外原料。
- [ ] 原料守恒：`cook` 前后 `raw`/`ready_food` 总量守恒。

## 6. M4 · 员工岗位与雇佣

### 玩法目标
把「点单/送餐/补餐」从自动 worker，变成**可雇佣、可排班、可成长**的决策。

### 规则设计
- **岗位**从 1 种（补餐露米）扩到 **3 种**：点单员、送餐员、补餐员。
- **雇佣**：每个岗位都可雇佣一名员工（`employee` 布尔改为 `staff: {order:bool, deliver:bool, refill:bool}`），雇佣要一次性费用 + 日工资。
- **未雇佣岗位的代价**：没有点单员 → 客人主菜等待变长（玩家可亲自去点单）；没有送餐员 → 玩家亲自送；没有补餐员 → 食材台缺货更快（玩家亲自补）。
- **成长**：每个员工有独立经验/等级，影响速度或携带量（复用现有 `staff_exp/staff_level/staff_capacity`，改为按岗位分别计）。
- **排班**：准备期可指派「优先照看某分区」（现有 `staff_zone` 逻辑扩展到每个岗位）。

### 数据接入
- `service_team` 目前固定 2 个自动 worker（点单/送餐），改为「有员工则用员工实体，无员工则该岗位由玩家承担或降速」。
- `employee` / `staff_exp` / `staff_zone` 扩展为按岗位的结构；旧字段迁移。
- `hire()` 从单次招聘改为「按岗位招聘」。

### 存档字段
- `staff: {order:{hired,exp,zone}, deliver:{...}, refill:{...}}`，迁移自旧 `employee/staff_exp/staff_zone`。

### 验收测试（新增 `tests/staff.gd`）
- [ ] 无点单员时，主菜等待显著变长（有可测阈值）。
- [ ] 雇佣各岗位后，对应环节自动恢复。
- [ ] 各岗位经验/等级独立成长，携带量/速度按等级提升。
- [ ] 工资按「已雇佣岗位数」结算，守恒。

## 7. 建议的第一批（Sprint 1）

> 只做 **M1 + M2**，因为它们是最小可验证的「有取舍菜单 + 有因果口味」，且是 M3/M4 的地基。

**交付物：**
1. `systems/dishes.gd`（菜谱表驱动）+ `systems/patrons.gd`（顾客偏好模板）。
2. `main.gd` 接线：菜单选择、点单、结账改用新表。
3. 存档 `version=5` + 迁移。
4. `tests/dishes.gd` + `tests/patrons.gd` 通过，CI 绿。

**明确不做（Sprint 1）：** 火候小游戏泛化（M3）、岗位拆分（M4）。
